# 多分辨率与 HUD 自动锚定

## 为什么不能只用截图尺寸

原神的「UI 边界偏移」会让 HUD 向内收缩，背景仍然铺满截图。它是游戏内部设置，不等于 Android 的 DisplayCutout，也不能把设置数字直接当成截图像素。

2026-11-07 连接的 24117RK2CC，截图 2400×1080，用户确认游戏 UI 边界偏移为 60。旧算法从 3040×1904 参考图得到缩放 0.5672；实际图标测得约 0.6308，左右边距约 89.7 像素。只外扩搜索框不能修复模板尺寸、小地图范围和触控坐标。

## 自动标定

`GameUiCalibrator` 复用素材配置中的参考矩形和原始灰度模板：主界面用派蒙，地图用左下设置，对话用历史图标。右上地图关闭按钮只用于复核和独立测量右边距，不单独建立标定，避免普通页面的叉号误触发。

初次在限定的角落区域进行多尺度匹配，粗搜范围是旧比例的 0.75～1.55 倍，再细搜，最低相关分数 0.90。同时验证上下贴边位置及横向边距范围，拒绝内容区的相似图案。左侧观测不足以确认右边界时先按原神默认左右对称估算；进入地图看到右侧锚点后独立补测，支持非对称边距。

保留完整截图，仅在参考坐标换算时使用 HUD 有效边界。对于参考图宽 W、高 H、测得缩放 s、当前截图宽 w、高 h、左右边距 L/R：

- 左锚：`x = L + referenceX × s`。
- 右锚：`x = w - R - W × s + referenceX × s`。
- 中锚：`x = (w - W × s + L - R) / 2 + referenceX × s`。
- 上、中、下纵向偏移分别为 `0`、`(h - H × s) / 2`、`h - H × s`。

模板尺寸使用同一个 s；模板框、独立搜索框和 OCR 区域共用变换。1920 宽识别图会同步缩放标定，命中坐标仍经原有 ScaleConverter 返回原生截图。小地图裁剪、PhoneHud、头像初始区域和 GameInput 的参考点共用这份标定。PC 参考图等不同画布保持原有公式。

每三秒最多复核一次，已命中时先走单尺度检查。没有可信锚点时保留上次结果；尚无标定时回退原算法。标定仅保留在当前共享会话，停止共享、改变截图尺寸或旋转时清除，不写入跨设备配置。只复用同宽高比的缩放图，拒绝套用到其他画面尺寸。

手机队伍头像还可能整体上移。`PartyRecognition` 先尝试原始位置和上次成功的列表位置，失败后在右侧有限范围内共同定位三个等距头像；只接受三个不同角色、达到各自分类阈值且平均置信度大于 0.85 的列表，缓存整个列表的平移。尺寸或映射改变会清除缓存，空白和重复头像仍拒识。

## 真机诊断

Debug 包可通过受 DUMP 权限保护的广播获取只读诊断，不点击游戏、不改开关：

```powershell
adb shell am broadcast -n com.bettergi.pocket/.debug.DeviceAutomationReceiver -a com.bettergi.pocket.debug.HUD
adb pull /sdcard/Android/data/com.bettergi.pocket/files/hud-diagnostic artifacts/hud-live
```

要求已开启屏幕共享，地图追踪独占运行时不执行。报告包含标定、主界面/地图判断、关闭按钮、小地图矩形、地图缩放、对话选项和可见队伍。截图和报告只保存到应用外部私有目录及本地 artifacts；不要把包含 UID 的整屏截图作为测试资源提交。

## 能否直接读取 UI 边界偏移设置

本机实测 `run-as com.miHoYo.Yuanshen` 返回 package not debuggable，访问 `/data/user/0/com.miHoYo.Yuanshen/shared_prefs` 返回 Permission denied。可访问的外部配置入口尚未发现该设置。因此未依赖私有配置格式，也未尝试 root 或修改游戏文件。设置页显示值可通过截图 OCR 读取，但仍需换算内部单位；直接测量最终 HUD 边界可以适应用户修改设置。

## 验证范围

JVM 回归使用真机局部截图，而非粘贴生产模板伪造正样本，覆盖派蒙、多尺度、左右边距、非对称补测、1920 宽缩放图、同源 ROI、旋转/其他参考图回退及空白/错位拒识。完整截图留在 artifacts。

Android 原生模型测试增加 `classifiesCutoutPhoneWithShiftedPartyStrip`，验证新手机的绮良良、八重神子、哥伦比娅、位置缓存和空白拒识；原平板头像识别保持通过。厂商可能冻结后台 instrumentation 进程，执行时应保持 ADB 与应用交互，避免把进程冻结误判为推理卡死。

主界面和地图页的实时共享帧已确认识别，地图关闭坐标为 (2213,61)，小地图区域为 (167,23,265,265)。实时画面已识别三个后台角色，并使用识别坐标通过应用无障碍切到绮良良、识别到隐藏的迪希雅后切回。这不代表完整采集路线、所有自定义按钮布局或所有手机均已验证。旧 CPU 亲和性专项测试在新手机上出现系统限制（请求恢复掩码 ff，实际为 fc），需与 HUD 适配测试区分。

地图追踪实测还发现地区名单顶部的「游逸旅闻：蒙德 璃月 稻妻」可能先于真正选项被 OCR 命中。地区匹配现在拒绝带其他汉字的提示文本，保留邻近图标识别为「工」的兼容，并在名单关闭后才记录选择成功。

小屏缩放还会让相机闭环的 2～3 度差角舍入为 0 像素，无法进入 2 度容差。GameInput 对非零差角至少保留一个原生像素的方向修正，零差角仍不派发；CameraControl 的 PC 对拍公式保持不变。

进度悬浮条覆盖地区按钮时，只有 NOT_TOUCHABLE 标志不足以保证游戏收到点击。穿透期间窗口透明，并将只读日志正文一起处理；遮挡判断改用 View 的实际屏幕位置，适应挖孔安全区带来的窗口定位差异。

2026-11-08 雪景续测发现，派蒙原始矩形模板包含旧场景背景，明亮雪景的普通相关分数仅约 0.76。改用派蒙亮色轮廓的前景掩膜，填回眼睛等内部暗部后匹配，样本分数约 0.95，保持 0.90 的标定门槛。掩膜相关产生的 NaN/Infinity 明确拒绝。该掩膜同时用于主界面判断和自动标定。

摇杆中心的横向位置使用有效 UI 宽度中的比例，纵向仍按距底边的缩放距离。2400×1080 样本中的中心约 (440,825)；单纯左锚会得到约 x=391，导致前推带有横向分量。相应回归检查前推触点位于真实中心上方。

穿透点按从路线工作线程等待窗口输入标志更新后再派发，避免刚设透明时 DOWN 仍落在上一帧的悬浮窗上；等待不阻塞应用主线程，中断时撤销穿透。

## 2026-11-08 地图追踪续测结果

最新构建与 180 项 JVM 测试通过。实际运行的短段取自「04-风车菊-风起地3」的前两个点（南风之狮的庙宇传送点及首个地面路径点），原路线资源未修改。保留原行走位和续盾设置，实测完成自动打开地图、选择地区、传送、四人队伍识别、绮良良短按续盾、返回迪希雅、转向行走、到点及终点停留拾取流程；01:09:54 日志为完成 1、失败 0。流程完成不等于证明获得了风车菊，未观察到实际获得物品提示，不计为采集成功。

验证不覆盖完整长路线。星落湖路径会进入水中，游戏明确提示「游泳时不能切换角色」；现有 motionStatus 未识别游泳，续盾切人会失败。风起地神像与钓鱼点重叠时会弹出选择列表，现有传送流程尚未处理该列表。完整地面路线后段仍遇到地形卡死，不能将本次首段通过描述为整条路线或所有地图追踪场景通过。用户确认其中一次曾手动触屏中断持续手势，该次取消和释放异常不作为无干预回归结果。

临时关闭切人的测试设置已逐字节恢复原备份；随后通过的短段使用原设置。测试图片、完整日志和临时路线留在本地 artifacts，不提交用户整屏画面。

短段自然结束后，再通过应用无障碍点开并关闭大地图均成功，确认该次结束没有残留持续触点。随后重启服务清除内存中的调试路线覆盖，并恢复屏幕共享；原地图追踪设置与备份逐字节一致。

## 2026-11-08 TB322FC 换设备复测

新连接设备 TB322FC（3040×1904）覆盖安装最新 Debug 包，保留应用数据。自动标定为 scale=1.0、leftInset=0、rightInset=0，未套用上一台挖孔手机的边距。共享和无障碍连接正常。

通过正式执行器两次运行南风之狮的庙宇地面首段，均在大地图双指缩放阶段停止：第一次 5.38→目标 4.92，实际 5.34；第二次 5.34→目标 4.92，实际仍 5.34。两次均完成 0、失败 1，尚未进入该轮传送后的行走，不能认定路线在平板最新版上正常可用。此轮没有修改缩放算法，问题证据保存在 artifacts/tablet-route-verification.log。

失败结束后通过应用无障碍点击关闭地图成功，未观察到残留持续触点。临时调试路线仅在内存中使用，未写入路线选择偏好。

复测结束后重启应用清除了内存中的临时路线覆盖，恢复无障碍连接，并返回原神。屏幕共享随测试停止，后续运行需重新授权共享。

后续已将地图缩放作为独立问题修复并完成 TB322FC 双方向实测；最新结果、系统残留触点问题与验证边界见 [地图缩放修复与验证](地图缩放修复验证.md)。上面的两次缩放失败保留为修复前记录。
