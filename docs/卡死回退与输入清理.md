# 卡死回退与输入清理

2026-11-08，设备 HA28G57W（TB322FC）。本轮按用户要求简化卡死脱离，测试范围仅地图追踪。

## 当前策略

- 任务启动、每条路线、路径段重试、每个点位执行前清空排队点按和持续触点，并等待实际抬手完成。对应退出路径也通过 finally 清理，包含异常和用户停止。
- 卡死后先释放全部输入，以本次实际定位和上一点位的中点作为回退目标。回退完成后重新定位、重新转向，再走原目标点。
- 回退直接使用原路线工作线程，不新建脱离线程。只转向和短步行走，去掉旧随机偏角、左右横移、跳跃和攻击组合。
- 没有有效上一点位、定位失败、回退超时或转向失败时，退出回退并交给路径段重试。回退循环检查 30 秒时限；退出时全释放。停止信号仍由原路线运行时处理。
- 清理未确认时不继续提交新操作。摇杆或视角手势提交失败也不再静默当作成功。

## 持续触点问题

此前真实日志出现 InputDispatcher 的重复 pointer id 10，之后触控持续被系统拒绝。这解释了部分旧脱离动作没有实际发生：源码有分支和提交调用，并不等于游戏收到了动作。

合成手势现在保证续接旧触点排在新触点之前。持续移动期间反复点按或重新按住视角时，按新触点数量控制当前输入流的长度：达到预算先合法续接抬起全部触点，收到完成回调后再恢复仍需要的按住状态。停止时清空排队操作，不重新按住或补发旧点按。

该流程使用原有无障碍主线程和完成回调，不另开操作线程。若抬手被取消或未能确认，则停止后续手势，不能把空的本地触点列表当作系统已经释放。

已经在旧版运行中丢失记录的系统触点，测试前曾通过 ADB 一次性清理；这不是应用运行依赖，也不证明新版本能自动恢复任何已损坏的旧系统输入状态。

## 实测及边界

12:50:21，在原路线线程内通过 Debug 请求强制触发一次同路径回退，目标地图坐标为 `(15112.353, 20171.672)`；12:50:34 记录回退完成并重试原目标，12:50:40 到达该目标。日志线程编号始终为 19088。

该次路线后续仍出现重复触点编号，用户随后手动操作并停止了游泳中的角色。因此只确认该次回退及恢复目标点，不能将整条路线记为无干预通过。触点预算重建是在这次失败后补上的，尚未在最终版本上重新跑完整路线。

最终版本验证：

- 189 项 JVM 测试通过，覆盖回退中点、同调用线程、取消/异常清理、释放失败阻止移动，以及任务间输入清空。
- 10 项 Android 手势回调测试通过，覆盖旧触点续接顺序、停止期间的重建及排队点按清空。这些测试使用真实 StrokeDescription，但由测试控制派发回调。
- 1 项真实系统输入压力测试通过：在专用 Debug 测试界面持续按住摇杆、反复移动及重建视角触点，交错点击 40 次，界面实际收到 40 次，事件触点集合一致，最终无按住触点。该测试没有向原神注入压力动作。
- Debug 和 AndroidTest APK 构建成功，Debug 已覆盖安装到设备。最终测试后保持原神路线停止。

真实压力测试启动时，instrumentation 会重启应用进程；需重新绑定已授权的无障碍服务，并设置 `accessibility_enabled=1`，否则测试会在连接检查阶段失败。不得把这种前置失败算成手势执行失败或通过。
