# 构建与发布

本文面向项目开发者和维护者，介绍 Windows 本地构建、GitHub Actions 打包、APK 签名与 GitHub Release 发布。应用下载、授权与使用方法见 [README](../README.md)。

## 本地构建

所有命令均在仓库根目录执行，仅输出 `arm64-v8a`。完整版包含自动剧情和地图追踪，剧情版只保留自动剧情及其配套功能。

构建所需地图和路线资源通过 `tools/sync-pathing-assets.ps1` 同步，不存入 Git。

构建命令：

```powershell
# 完整版先同步地图资源及地方特产路线
./tools/sync-pathing-assets.ps1
./gradlew.bat :app:assembleRelease -PincludePathing=true

# 精简版无需准备任何地图资源
./gradlew.bat :app:assembleRelease -PincludePathing=false
```

`includePathing` 默认为 `true`。两次构建使用相同的输出位置 `app/build/outputs/apk/release/app-release-unsigned.apk`，需要保留两个包时请先复制第一次的输出；本地可改用 `assembleDebug` 获得默认调试签名 APK。

## GitHub Actions 与 Release

GitHub 仓库的 **Actions → Build arm64 APKs (story + full) → Run workflow** 手动触发一次，会构建、验证并签名两个 APK；没有 push 或 PR 自动触发。在该次运行的 Artifacts 中分别下载：

| 构建物 | 包含的 APK | 功能 |
| --- | --- | --- |
| `bettergi-pocket-arm64-story-运行编号` | `bettergi-pocket-arm64-story.apk` | 仅自动剧情及配套功能 |
| `bettergi-pocket-arm64-full-运行编号` | `bettergi-pocket-arm64-full.apk` | 自动剧情 + 地图追踪 |

SHA-256 显示在运行摘要。单元测试独立执行，失败不阻断后续构建、签名或上传；仅在测试失败时额外上传诊断报告 `unit-test-reports-运行编号`。

手动触发时可勾选 **publish_release**，并在 **release_version** 填写版本号（如 `1.0.1`，也可填 `v1.0.1` 或 `1.0.1-alpha.1`）。勾选发布时版本号必填，标签自动使用 `v版本号`。发布成功后，上述两个已签名 APK 会作为 Release 附件上传。已有同名标签时会在构建前报错，不覆盖旧版本。Release 链接显示在运行摘要；未勾选时只生成 Actions 构建物，使用代码中现有版本。

### 版本号与自动写回

仓库根目录的 [version.properties](../version.properties) 是版本信息的唯一来源，`app/build.gradle.kts` 从中读取 `VERSION_NAME` 和 `VERSION_CODE`。

发布流程如下：

1. 从分支触发工作流，勾选 `publish_release`，填写 `release_version`。
2. 构建前将填写的版本写入 `VERSION_NAME`；版本变化时，将原来的 `VERSION_CODE` 加一，两个 APK 使用同一组版本信息。重复处理同一版本不会再次递增。
3. 两个 APK 构建、资源检查、签名、上传成功后，由 `github-actions[bot]` 将 `version.properties` 单独提交并推送回触发构建的分支。
4. 以版本提交创建标签和 GitHub Release，上传同一轮构建的两个 APK。

版本更新脚本为 [set-release-version.ps1](../tools/set-release-version.ps1)。只写回版本配置，不将下载的地图、签名文件或其他构建输出提交到仓库。源码写回使用普通快进推送；分支在构建期间有新提交时会停止，需基于最新代码重新发起构建。只支持从分支发布，不支持从已有标签触发自动写回。

Release 任务使用工作流自带的 `GITHUB_TOKEN` 和 `contents: write` 权限，无需额外配置 PAT。目标分支需允许该机器人提交；如果分支保护拒绝推送，流程会明确报错并停止发布。

## 地图与路线资源

地图资源不需要提交到 Git：工作流自动下载并校验 BetterGI 使用的 `BetterGI.Assets.Map 1.0.26` NuGet 包，从固定 BetterGI 提交获取 `tp.json`，再从 [bettergi-scripts-list 的 release 分支](https://github.com/babalae/bettergi-scripts-list/tree/release/repo/pathing/地方特产)仅拉取特产路线。运行摘要记录实际路线提交号。地图准备逻辑见 `tools/prepare-ci-pathing-assets.ps1`，最终 APK 检查见 `tools/verify-apk.ps1`。

## 签名与 Secrets 配置

正式发布可在仓库 **Settings → Secrets and variables → Actions** 配置 `ANDROID_KEYSTORE_BASE64`（签名文件的 Base64）、`ANDROID_STORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD` 四项 Secrets。未配置时会生成同次运行共用的临时测试密钥，两个包可以安装，但不同运行之间需要卸载后重装；使用固定发布密钥可持续覆盖升级。两个版本使用同一应用 ID，可相互覆盖切换。可选配置 `BAIDU_MTJ_APP_KEY`，为空时不启动统计。

已有签名文件时，使用原文件和密码，不需要生成新密钥。在上述页面逐个点击 **New repository secret** 添加：

| Secret 名称 | 填写内容 |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | 现有 `.jks` / `.keystore` 文件的完整 Base64 内容 |
| `ANDROID_STORE_PASSWORD` | 密钥库密码（Store password） |
| `ANDROID_KEY_ALIAS` | 签名密钥别名（Key alias） |
| `ANDROID_KEY_PASSWORD` | 该别名对应的密钥密码（Key password）；原来与库密码相同时填写相同值 |

在 Windows PowerShell 中，将路径改为现有签名文件的位置，再复制 Base64 到剪贴板后粘贴到 `ANDROID_KEYSTORE_BASE64`：

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path 'D:\签名\release.jks').Path)) | Set-Clipboard
```

忘记别名时可运行 `keytool -list -v -keystore 'D:\签名\release.jks'`，按提示输入密钥库密码，查看 Alias name。只配置部分签名 Secrets 会报错；勾选 `publish_release` 时必须完整配置四项固定签名 Secrets，不允许使用临时测试密钥发布。签名文件和密码只放到 Secrets，不提交到仓库。
