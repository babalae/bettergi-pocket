# 地图缩放修复与验证

2026-11-08 后续按用户要求进一步简化为「放大到普通传送锚点可见，然后保持比例拖图」，取消下面早期版本的越过目标再返回动作。当前方案与挪德卡莱完整路线实测见 [挪德卡莱特产路线实测](挪德卡莱特产路线实测.md)。下面保留早期修复过程与其验证边界。

## 问题与实现

2026-11-08 在 TB322FC（3040×1904）上复现：大地图等级约 5.34，目标约 4.92，原双指开合后滑块没有明显移动，路线在传送前停止。这是独立的地图缩放控制问题。

旧实现把 `current / target` 直接当作指间距倍率，本例每根手指仅移动约 20 像素；没有校准 Android 游戏对这种手势的实际响应。对照参考项目 `TpTask.AdjustMapZoomLevel` 的操作后读回机制，Android 改为直接控制游戏左侧缩放滑块：

1. 从新截图识别真实滑块中心，作为按下位置。
2. 轨道两端与滑块使用同一个锚定变换，等级 1 在上端，等级 6 在下端，插值得到目标原生坐标。
3. 保持同一触点完成拖动。小幅调整先经过至少轨道长度 16% 的起步行程，再回到目标；靠近末端时向另一侧起步，避免越界。这个保护已实际验证可用，但本轮不能单独证明短行程阈值就是此前反向失败的原因。
4. 抬手并等待画面更新后重新识别。实际误差不超过 0.15 才算成功，保留无进展与次数限制，不把手势提交成功算作缩放成功。

没有降低识别门槛、放宽误差或改动路线资源与用户设置。

## 单独发现的系统残留触点问题

补测期间，不仅缩放，点地图和系统授权按钮也不生效。InputDispatcher 明确记录旧注入设备 `DeviceId(-1)` 仍有触点 `{10, 1}`，拒绝后续 DOWN、MOVE、UP。单次 swipe 和增加起步行程的拖动在该状态下均无效，因此这些失败不能单独用来判断缩放行程是否正确。

依据日志中的触点编号，通过仅在 ADB 下运行的本地恢复程序清理后，同一正式执行器立即完成了上表的双方向复测。当前异常状态已清理；本轮没有修改持续触点合成器，也没有完成残留触点产生原因的长期修复。恢复程序只在本地 artifacts，不作为应用正常运行的依赖。

无障碍手势完成回调不足以独立证明下游输入已被游戏接受；AOSP 的 [MotionEventInjector](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/MotionEventInjector.java) 在派发流程中通知完成。本次是否恢复以实际缩放反馈、传送和点开/关闭地图的截图为依据。
