# 队伍识别与元素采集

## 使用

悬浮球 → 地图追踪「开始」→「设置」：

- **行走位**：有序多选候选角色，按已选顺序匹配当前队伍；不在队伍中的候选自动跳过。默认名单为迪希雅。
- **生存位 · 循环短战技**：有序多选，默认绮良良、莱依拉、茜特菈莉、芭芭拉、七七。
- **生存位 · 循环长战技**：有序多选，默认钟离。先匹配短战技组，再匹配长战技组。同一角色切到另一组时自动从原组移除，避免同时配置长短按。
- **续盾间隔**：单位秒，0 使用匹配角色资料中的战技冷却；手动值为 1～3600 秒。
- **水 / 雷 / 风 / 火元素采集**：每种元素分别多选候选角色，默认按 PC 角色资料填入该元素全部具备采集能力的角色。只在路线包含 `hydro_collect`、`electro_collect`、`anemo_collect`、`pyro_collect` 时执行。先按名单顺序选出在队角色，再按能力执行普攻或战技；重复战技会等待记录的冷却。采集后返回行走位。

点击设置项的 ▾ 展开悬浮下拉框。支持中文名、英文名、配置别名搜索；已选置顶，已选标签按优先级排列，点击标签 × 可移除，用列表中的 ↑ ↓ 调整顺序。支持全选当前筛选结果、清空、恢复默认。点击“确认选择”才保存，“取消”或点击外部会放弃草稿；切换搜索条件不会丢失已选角色。

清空某项表示关闭该项。旧单选角色自动迁移成单元素名单，旧“自动”展开成默认候选，旧关闭状态保留。新设置用有序 JSON 数组保存，重启仍保留优先级。修改在下一次开始路线时生效，原有地图匹配方式、小道具独立开关和自定义间隔继续保留。自动续盾只在地面普通行走、距离目标大于 10 时触发，不在飞行、攀爬、游泳或跳跃点期间触发。

识别要求为**单人模式、四人队伍、主界面无遮挡**。队伍初始化会先切到一个可见角色，以识别原先隐藏的当前角色。首次使用或传送后会重新建立完整队伍。全部候选均不能满足路线所需元素、头像低置信度或切人失败时，当前路径段失败并写日志；批量队列沿用原来的失败处理方式。不能在执行期间手动换队伍。

## 手机适配

手机只显示三个后台角色头像；当前角色隐藏，切人后头像列表重排。因此不能把屏幕上三个位置视为 PC 的队伍 1～4 号位。

`PartyRecognition` 每次从三个已标定区域识别头像。`PathingParty` 点击目标头像后，必须确认目标消失、其余两人保留且原来的当前角色出现，才接受切人成功；最多重试三次。后续切换重新识别位置。衣装类别统一映射到基础角色；NPC、派蒙和龙等训练类别没有可操作资料，作为无效识别处理。

头像矩形放在 `app/src/main/assets/pathing/layout.json` 的 `partyAvatars` 中，按从上到下排列，使用 TopRight 锚定。当前标定来自 `Pocket/1.png` 的 3040×1904 画布：`(2820,480,150,150)`、`(2820,660,150,150)`、`(2820,840,150,150)`。其他 UI 缩放、分辨率或安全区需要实机重新确认。

普通路线关闭行走位、生存位且没有元素动作时，不加载模型、不主动切人。纳西妲长按转向采集、自动战斗、自动换整队仍不支持。

## 模型与构建

- `recognition/Party/avatar_side_classify_sim.param/.bin`：用户提供的 ncnn 模型，原样导入。
- `avatar_labels.json`：从 PC 编译目录 2026-10-24 版同名 ONNX 的 `names` 元数据按输出序号提取，共 162 类，包含衣装和 NPC 类别。不能根据中文角色名或目录排序重新生成标签。
- `combat_avatar.json`：原样复制参考项目 `GameTask/AutoFight/Assets/combat_avatar.json`，SHA-256 为 `33de4a3c1a3899d80d79070d525a088c67b24fe6080e34297b8a958f1944df61`，与参考文件逐字节一致。中英文名称通过 `nameEn` → `name` 字典映射，等同 PC 的 `DefaultAutoFightConfig.CombatAvatarNameEnMap`；衣装去后缀后再查此字典，等同 `CombatScenes.ClassifyAvatarCnName`。同时沿用配置中的元素采集能力、元素类型和战技冷却。
- `model-info.json`：输入输出约定、来源和资源 SHA-256。推理使用 `in0` → `out0`、RGB 64×64、`1/255` 归一化；模型已含 Softmax。
- ncnn CPU SDK 固定为 **20260526**，CMake 下载官方源码并校验 SHA-256，以 `NCNN_OPENMP=OFF` 编译，参见 [官方接入文档](https://github.com/Tencent/ncnn/wiki/use-ncnn-with-own-project)。首次原生构建需要联网，NDK `28.2.13676358`、CMake `3.22.1` 由 Android SDK 管理。支持 armeabi-v7a、arm64-v8a、x86_64，JNI 链接使用 16 KiB 页对齐；静态依赖符号不向其他原生库导出。
- 原生 SDK 的 BSD 许可证随包保存在 `assets/licenses/ncnn.txt`。参考 ONNX 元数据声明模型为 AGPL-3.0，沿用参考项目和模型原有许可。

模型实例仅在路线工作线程中使用，路线结束、失败或取消时释放。为了保持导出模型的分类一致性，关闭 ncnn packing 和 FP16 运算/存储优化；权重文件保持原始内容。`Mat::total()` 包含通道填充，不能用于检查 162 个输出的逻辑数量。

2026-11-07 真机曾在路线启动时出现 `SIGABRT`：`load_model` → `Mat::from_float16` → `Cast_arm::forward` → LLVM OpenMP CPU 拓扑初始化，因可用 CPU 数与拓扑线程数不一致而断言失败。它发生在将 FP16 权重转换为 FP32 的阶段；降低单个网络的 `num_threads` 不能保证权重加载避开 OpenMP，因此从构建中移除该运行库，使用单线程 CPU 推理并保留 SIMD 优化。模型 `.param/.bin`、输入预处理和 162 类标签顺序均保持原样。参考 BetterGI 当前源码中 PC 侧走 ONNX 分类器，Android 使用这里的 ncnn 资源和 Android ABI 原生库；模型资源与执行它的原生运行库需要分开看待。

## 验证

三种 ABI 的 debug 构建及 JVM 单元测试通过。`AvatarCatalogTest` 逐项检查 128 条 PC 配置的名称、元素、采集能力及冷却映射，并检查衣装和 NPC 分类处理。

`lintDebug` 另有三项既有错误：`InputAccessibilityService` 的 UsageStats 权限声明、`GestureComposer` 的 API 26 调用、`PathingRouteWindow` 既有拼音转写调用的 API 29 检查；未通过整项目 lint，不影响上述 APK 构建及测试结果。

`OrderedAvatarSelectionTest` 验证多选草稿、排序、去重、清空和旧单选迁移。`AvatarMultiSelectInstrumentedTest` 在真实悬浮设置窗口验证搜索、跨筛选多选、优先级调整、确认保存、取消撤销和恢复默认，测试结束恢复用户原设置。

`PathingPartyTest` 使用模拟的四人队伍、截图识别结果、时钟及触控，验证头像重排、隐藏角色发现、切人确认失败、元素普攻/战技、战技冷却、续盾间隔、返回行走位、取消长按后的抬手。

`NcnnPartyInstrumentedTest` 在连接的 TB322FC（Android 16 / arm64-v8a）上直接加载 APK 中的 JNI 和模型，确认用户截图中的桑多涅、七七、奥黛塔及空白画面的拒绝行为。测试图只保留三个头像区域。该测试不对游戏注入操作，因此不等同于实机跑图续盾、真实采集点的端到端验证。

关闭 OpenMP 后，三种 ABI 的 Debug 构建通过，检查三个 `libpocket_ncnn.so` 均没有 OpenMP 运行库符号。真机测试新增受限 CPU 工作线程中的三次模型创建、识别和释放，并单独运行该用例覆盖冷启动；原头像分类和空白拒识仍通过。受限 CPU 用例覆盖额外运行条件，不保证复现原先的偶发拓扑断言。

```powershell
./gradlew.bat :app:assembleDebug :app:testDebugUnitTest
./gradlew.bat :app:assembleDebugAndroidTest
./tools/android-device.ps1 deploy -SkipBuild
adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb shell am instrument -w -e class com.bettergi.pocket.pathing.party.AvatarMultiSelectInstrumentedTest com.bettergi.pocket.test/androidx.test.runner.AndroidJUnitRunner
```

真机测试使用上述覆盖安装加直接 instrumentation 的方式。当前 Gradle `connectedDebugAndroidTest` 默认在结束后卸载被测应用，会清理设备上的设置；不要对保留用户配置的设备使用该默认流程。多选版本通过 157 项 JVM 单元测试和上述真实悬浮窗口交互测试。
